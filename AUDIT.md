## Локальні результати

- Linux / Python 3.13: **538 passed, 2 skipped**, фінальний прогін після оновлення локального рушія.
- Покриття прогону: **76,73%** коду програми, без тестів/скриптів.
- Ruff і mypy (10 модулів) проходять. Оновлені звичайний, EXE та local-model lock-файли:
  pip-audit не знайшов відомих вразливостей. Перевірку старих гілок Python також виконано;
  виявлені Pillow 12 / Stanza / filelock усунені з підтримуваної конфігурації.
- RapidOCR 1.4.4, production CPU factory, обмеження 1600 px: синтетичні 1080p/1440p,
  медіани **0,694 / 0,833 с**, по два повтори. Після inference — близько **0,00005–0,00009 CPU с**
  за секунду очікування. Замір виконано з OpenCV 5.0.0.93; фінальний lock містить 5.1.0.95.
  Це не FPS і не порівняння з грою.
- App у простої на Linux/Xvfb з реальними хуками: **0,315% одного ядра** протягом 5 с,
  після 1 с прогріву. Вимірювання коротке й залежить від машини.
- Справжній local-model native smoke із CTranslate2 4.9.0 / SentencePiece 0.2.3:
  Arabic→Latin transliteration fixture, результат `مرحبا → marhaba`, CPU 1/2, мережа заблокована.
  Це перевіряє інсталяцію формату, токенізацію та native inference, не якість English→Ukrainian.
- Оглянуто реальні PNG Tk-картки, бібліотеки та накладок Linux. Вони не додаються у source tree;
  Windows Segoe/DPI, Credential Manager/DPAPI та EXE перевіряє Windows CI.

Без ПК користувача не підтверджуються змішані монітори/DPI, захоплення конкретного ігрового шрифту,
поведінка накладки в Mafia та падіння FPS після pause/resume. Є засоби збирання потрібних даних.
Реальні платні API без ключів перевірені лише контрактами; ключі для цієї роботи не запитувались.

Нативні прогони також допомогли виправити бібліотеку: мінімальна ширина редактора тепер
обчислюється за його вмістом, щоб колонки списку не обрізались через сталий резерв 500 px.

та не входять у модальний цикл нативного меню без користувача.

Завантаження програми не містить особистої бібліотеки, ключів, конфігурації, журналів або згенерованих PNG/XML.
Причину просідання FPS у Mafia цей CI не встановлює; для вимірювання є docs/PERFORMANCE.md.

## Оптимізація запуску 8.5.1 — 19.11.2026

Запит користувача: запуск Windows EXE займає 5–15 с. Такий час на його ПК тут не відтворювався.
Прибрано дві підтверджені зайві роботи до появи вікна: перевірка Tesseract імпортувала
pytesseract/Pillow/NumPy, а створення провайдерів одразу імпортувало requests/SSL.
Перевірка Tesseract тепер викликає лише executable з тайм-аутом 2 с та перевіряє код завершення;
HTTP-сесія створюється на першому запиті під спільним lock зі збереженням headers/cookies/пулу.
Без записів recovery не завантажується psutil. OCR-моделі й раніше підключались при використанні.

Нова перевірка запускає окремий процес зі справжнім Tk-вікном та глобальними слухачами:
через 300 мс працює інтерфейс із чотирма вкладками, а numpy/cv2/onnxruntime/RapidOCR,
CTranslate2/SentencePiece, pytesseract/pygame/requests ще не імпортовані.
Окремі тести перевіряють код завершення й timeout Tesseract, повторне використання сесії/cookies,
серіалізацію запитів і порожню директорію відновлення. Packaged self-test також створює HTTP-сесію
та перевіряє CA-файл усередині frozen-пакета без мережевого запиту.

| Вимірювання | 8.5.0, медіана | 8.5.1, медіана | Скорочення |
|---|---:|---:|---:|
| Linux / Python 3.13 / source / Xvfb | 0,440 с | 0,255 с | 41,9% |
| Windows / Python 3.12 / справжні EXE | 1,083 с | 0,998 с | 7,8% |

У кожній серії по три окремі процеси на варіант, порожні ізольовані профілі, порядок запусків
чергується. Вимірюється час від створення процесу до головного вікна; Windows також перевіряє
відповідь на WM_NULL. Кеш файлів не очищено, перед Windows-заміром виконувалися збірка й self-test.
Це прогріті машини CI, не запуск після перезавантаження, перевірка антивірусом чи прогноз для ПК користувача.
Перша незалежна Windows-серія дала 0,895 → 0,803 с (10,3%); невеликі серії не дають гарантії стабільного відсотка.
[Повторна серія та її JSON-артефакт](https://github.com/SanchezKabanchez/Word_Lookuper/actions/runs/44595933847).

Підтверджено на коміті `7984af5d0897420d435bd7666bf1fe259fdf1255` після явного завантаження Tk helper у тесті:

- [Windows](https://github.com/SanchezKabanchez/Word_Lookuper/actions/runs/44597085482): **545 passed, 1 skipped**, 130,72 с.
- [Linux](https://github.com/SanchezKabanchez/Word_Lookuper/actions/runs/44597085515): **544 passed, 2 skipped**, 101,58 с; покриття **76,65%**.
- [Збірка EXE та повний packaged self-test](https://github.com/SanchezKabanchez/Word_Lookuper/actions/runs/44597085758) успішні.
- [Ruff, mypy, аудити та macOS core](https://github.com/SanchezKabanchez/Word_Lookuper/actions/runs/44597085446) успішні;
  на macOS ARM64 пройшов **21 core-тест** та імпорт Keychain-backend. Це не перевірка macOS GUI або збереження реального ключа.

Один попередній Windows-прогін виявив неініціалізований Tcl helper у перевірці Tab-порядку.
Тест тепер явно викликає `auto_load tk_focusNext` перед перевіркою тієї ж послідовності фокуса,
замість залежності від попередньої події фокуса у свіжому інтерпретаторі. Код програми ця зміна не змінює.

Журнал 8.5.1 містить час від входу в Python-launcher до появи вікна та етапи імпорту,
налаштувань/відновлення й кешу. Він дозволяє відокремити затримку всередині програми від часу
перед входом у Python, якщо 5–15 с на ПК користувача залишаться. Причину такої затримки без його заміру не встановлено.
